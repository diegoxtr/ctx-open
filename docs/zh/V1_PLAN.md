# CTX - 面向 V1 的目标、范围与计划
如果语言模型及其代理丢失了上下文，这就是你需要的工具。

## 1. 目的

本文定义：

- CTX 的产品目标
- 首个可用版本的功能范围
- 项目的知识产权立场
- 达到 V1 所需的开发阶段
- 启动真实用户测试的初始计划

其目标是对齐产品、架构、实现与验证。

## 2. 产品愿景

CTX 是面向结构化推理工作的认知版本控制系统。它不版本化对话，而是版本化显式认知工件：

- context
- goals
- tasks
- hypotheses
- decisions
- evidence
- conclusions
- AI runs
- reasoning evolution

愿景是让 CTX 支持可复现、可审计、且比不透明对话历史成本更低的 AI 工作。

## 3. 商业与产品目标

### 主要目标

构建可商业化的 CTX 基础，能够：

- 初始化本地认知仓库
- 记录结构化工件
- 生成优化上下文包
- 通过 AI provider 执行 runs
- 持久化可复现的认知提交
- 比较状态间变化
- 使用分支与合并
- 检测认知冲突
- 为真实测试提供操作可观测性

### V1 预期结果

一个可供小规模技术测试者使用的版本，用于验证：

- 工作模型的实际价值
- 认知工件的清晰度
- 决策可追溯性
- 冗余迭代减少
- 与真实 providers 协作的可行性
- CLI 流程质量

## 4. 它解决的问题

CTX 解决：

- AI 工作会话之间的上下文丢失
- 难以理解为何做出某个决策
- 已完成推理的重复
- 假设、证据与结论缺乏可追溯性
- 无法复现某个工作中的认知状态
- 反复发送无关上下文导致成本过高
- 缺少结构化推理的分支与合并机制

## 5. 产品范围

## 5.1 V1 包含的功能范围

V1 至少应包括：

- 本地 `.ctx/` 仓库
- 可用 CLI
- 结构化领域模型
- 可复现认知提交
- 认知状态 diff
- branching、checkout 与 merge
- 认知冲突检测
- `ContextPacket` 构建
- 通过可替换 providers 执行 `Run`
- 基础成本与使用指标
- 对 goals、tasks、hypotheses、decisions、evidence、conclusions 的检查
- 对 runs、packets、providers 与 metrics 的检查
- 对核心流程的自动化测试

## 5.2 V1 不包含的范围

V1 不包含：

- Web 或桌面 UI
- 网络多用户
- 远程同步
- 高级角色权限与安全
- 企业认证
- provider/plugin 市场
- 带复杂索引的高级语义引擎
- 通过 ML 优化 prompts
- 完整可视化 dashboard
- 深度 IDE 集成
- 共享服务器

## 7. V1 目标用户

初期验证用户：

- 软件架构师
- 平台工程师
- 使用 LLM 进行迭代工作的团队
- 技术研究者
- 需要决策可追溯性的人
- 希望降低对话成本与噪声的开发者

## 8. V1 价值主张

V1 必须证明：

- 结构化推理比原始对话更可复用
- 认知历史可按清晰规则进行版本化
- 迭代成本可衡量
- 推理冲突可作为显式实体检测
- CLI 足以进行早期产品测试

## 9. 当前项目状态

当前仓库已经包括：

- .NET 8 解决方案
- 分层架构
- 类型化领域
- `.ctx/` 文件系统持久化
- 核心操作 CLI
- OpenAI 与 Anthropic providers 以及离线回退
- 带认知冲突的 merge
- 核心自动化测试

这意味着项目不再处于构想阶段，而是在向可测试的 V1 收敛。

## 10. 达到 V1 的阶段

## 阶段 1 - 稳定基础

目标：

- 巩固技术核心，避免结构性返工

交付：

- 稳定领域模型
- 一致持久化
- 核心流程测试覆盖
- 必要 CLI 命令
- 基础错误处理一致

状态：

- 大部分已完成

## 阶段 2 - 认知仓库功能完整性

目标：

- 确保所有关键认知工件都可创建、检查、版本化与比较

任务：

- 补齐缺失的读取与导航命令
- 改进 CLI 提示与错误
- 强化按工件类型的 diff
- 改进 merge 与引导式冲突解决
- 确保实体间完全可追溯

退出标准：

- 技术用户无需手动编辑文件即可端到端操作 CTX

## 阶段 3 - 试点前的操作质量

目标：

- 让工具为低规模真实使用做好准备

任务：

- 加固输入校验
- 改进序列化与文件兼容性
- 添加诊断导出
- 添加清晰的操作日志
- 定义 `.ctx/` 仓库版本策略
- 确保提交与 packets 可复现

退出标准：

- 试点可在无需持续开发者协助下运行

## 阶段 4 - 真实 provider 集成

目标：

- 从模拟/受控模式过渡到带真实账户与生产模型的使用

任务：

- 加固 OpenAI 与 Anthropic 适配器
- 支持文件与环境配置
- 定义错误处理与重试
- 更精确记录成本
- 允许模型选择策略

退出标准：

- 测试者可以运行真实案例并衡量成本收益

## 阶段 5 - V1 试点

目标：

- 发布受控试用版

交付：

- 清晰安装方式
- 初始使用指南
- 测试场景
- 稳定命令
- 版本变更记录
- 文档化反馈回路

退出标准：

- 至少 3 到 5 名技术用户可完成真实流程并返回可执行反馈

## 11. 面向 V1 的开发 backlog

### 高优先级

- 更好的 `log` 导航与过滤
- 引导式认知冲突解决
- 通过文件与 secrets 配置 provider
- 仓库版本与迁移处理
- 更可读的提交间 diff 输出
- 端到端 CLI 集成测试
- 更完整的命令帮助
- 交叉引用校验
- 认知仓库 export/import
- workflow 文档

### 中优先级

- `.ctx/index` 中的搜索索引
- 更好的 `ContextBuilder` 启发式
- tag 支持与时间过滤
- 与提交绑定的 packet 快照
- 自动认知历史摘要
- 仓库统计命令

### V1 之后的低优先级

- 图形界面
- 远程同步
- 并发多用户协作
- 编辑器/IDE 集成
- server mode
- 可视化 dashboard

## 12. V1 的定义

当以下条件成立时，V1 才算存在：

- 仓库可初始化并在无需手动编辑 JSON 的情况下使用
- 所有主要认知工件都可创建、列出与查询
- 可构建上下文并执行 runs
- 提交可复现
- 状态 diff 有价值
- merge 能识别认知冲突
- 存在基础使用指标
- 自动化测试覆盖核心
- 文档足以支持技术 onboarding
- 至少一个受控试点可运行

## 13. 初始测试计划

## 13.1 试点目标

验证 CTX 是否在真实分析与开发场景中提升 AI 工作的质量与效率。

## 13.2 测试者画像

- 技术背景
- 熟悉 CLI
- 能够表述 goals、tasks、hypotheses 与 decisions
- 愿意记录结构化反馈

## 13.3 建议测试场景

- 新模块的架构设计
- 技术方案对比评估
- 复杂 bug 调查
- 基于证据的决策分析
- 带多重假设的产品迭代

## 13.4 观察指标

- 达到有用结论所需时间
- 重复迭代次数
- 重新发送上下文的量
- 记录决策的清晰度
- 恢复先前状态的难易度
