# CTX 商业与治理理念

如果语言模型及其代理丢失了上下文，这就是你需要的工具。

本文定义 CTX 如何在技术开放、项目控制，以及未来 monetization、licensing 或 acquisition 之间取得平衡。

## 目标

CTX 希望成为：

- 可本地使用
- 可修改、可扩展
- 通过 `.ctx` 格式保持可移植
- 可作为软件进行商业化
- 可作为战略资产受到保护

## 核心原则

CTX 应在实践上开放，但在治理上保持集中。

这意味着：

- 第三方可以使用它
- 第三方可以修改它
- 第三方可以在项目许可证下再分发
- 但官方方向、品牌、主仓库，以及未来重授权或出售所需的权利必须保持集中

## 为什么这很重要

如果项目在法律上分散到多个版权持有人，或者治理过度扩散，就会很难：

- 重新授权
- 签署商业协议
- 出售软件
- 将项目并入公司或完成收购

CTX 需要“操作上的开放”，但不能让所有权碎片化。

## 推荐治理模型

### 1. 明确的持有人

官方项目应有一个明确的 IP 持有人，或者由该持有人控制的法律载体。

当前：

- 初始持有人：Diego Mariano Verrastro

推荐演进：

- 当商业条件成熟时，将官方 IP 转移给一家公司

### 2. 受控的官方仓库

应存在一个单一官方仓库，其战略方向由持有人控制。

包括：

- 官方路线图
- 官方发布
- 官方许可
- 官方品牌

### 3. 通过 Assignment 或 CLA 管理贡献

如果目标是保留未来重授权、出售或重构的能力，外部贡献不应以“无条件自由”的方式进入。

因此 CTX 应保持：

- contributor assignment
- 或具有足够权利范围的 CLA

### 4. 品牌保留

`CTX` 品牌应与代码使用许可保持区分。

这能实现：

- forks：可以
- 商业混淆：不可以

## 商业理念

CTX 的核心业务是软件。

这意味着：

- 在许可证下允许本地商业使用
- 允许 self-hosted 部署
- 允许支持、集成与定制
- 未经单独许可，限制提供竞争性托管服务

## CTX 允许的事情

- 个人使用
- 专业使用
- 企业本地使用
- on-premise
- self-hosted
- 修改
- forks
- 在 CTX 许可证下再分发

## CTX 限制的事情

- 将 CTX 作为竞争性服务提供
- 将 forks 包装为官方发行版
- 以混淆方式使用 CTX 品牌
- 第三方假装自己是官方持有人并对官方发行版重新授权

## 未来收购

如果未来有公司收购 CTX，资产价值并不只在代码。

更有价值的是：

- 集中的版权
- 品牌控制
- 官方仓库控制
- 清晰的许可
- 规范化的贡献
- 与官方项目绑定的 `.ctx` 格式
- 围绕官方发行版形成的社区与采用

## 有利于出售的条件

为了让 CTX 保持 acquisition-friendly，应维持：

- 清晰的所有权历史
- 一致的贡献协议
- 一种允许当前模式且不阻碍未来重授权的许可证
- 官方项目与 forks 的清晰分离
- 可识别、可防御的品牌

## 应避免的事情

避免：

- 过早绑定社区治理
- 在当前阶段建立独立基金会
- 没有 assignment 或 CLA 的贡献
- 对“谁能重新授权”保持模糊
- 在没有中央协议的情况下形成多个持有人

## 随时间演进的推荐结构

阶段 1：

- 项目由创始人控制
- 使用清晰的 source-available 许可证
- 贡献受到规范管理

阶段 2：

- 若业务成熟，将 IP 转移到公司
- 建立正式商业协议
- 更正式地管理品牌

阶段 3：

- 商业发行
- 专业支持
- 企业化
- 潜在战略合作或收购

## 黄金规则

CTX 在使用和修改上可以开放。

但要让它在未来可出售，官方项目的所有权不能被稀释。
