# CTX 中的认知线程重建
如果语言模型及其代理丢失了上下文，这就是你需要的工具。

本文定义 CTX 应如何从结构化工件中正式重建上下文线程。

目标不是重放对话。

目标是重建：

- 为什么开启这条工作线
- 哪些假设为它提供了依据
- 出现了哪些证据
- 做出了哪些决策
- 哪些结论关闭了这个工作块
- 这些内容如何跨提交与分支演化

## 目标

为 CTX 提供一种规范方式来回答：

`我们是如何到达当前认知状态的`

这意味着能够重建：

- 某个实体的局部线程
- 某个任务或目标的线程
- 某个分支的线程
- 提交之间的时间线程
- 仓库级的整合线程

## 当前问题

今天的 CTX 已经拥有：

- 结构化实体
- 实体关系
- 认知提交
- 图导出
- 聚焦谱系

但它仍缺少对完整重建的正式定义。

这就造成了一个缺口：

- 你可以检查图
- 你可以查看提交历史
- 但没有一个规范算法来重建结构化的推理叙事

## 指导原则

认知线程不能来自聊天日志。

它必须只从以下结构中重建：

- `Goal`
- `Task`
- `Hypothesis`
- `Evidence`
- `Decision`
- `Conclusion`
- `ContextCommit`
- `BranchReference`
- `Traceability`

## 什么是认知线程

认知线程是知识演化的结构化、可证明序列。

它包含两个维度：

### 1. 语义维度

回答：

- 哪些工件彼此相关
- 依据链路是什么

示例：

```text
Goal
  -> Task
    -> Hypothesis
      -> Evidence
      -> Decision
        -> Conclusion
```

### 2. 时间维度

回答：

- 工件按什么顺序出现或变化
- 哪个提交记录了它们
- 它们在哪个分支中演化

示例：

```text
Commit A -> Commit B -> Commit C
```

## 重建类型

CTX 应支持以下正式重建。

### 实体重建

输入：

- `GoalId`
- `TaskId`
- `HypothesisId`
- `DecisionId`
- `ConclusionId`

输出：

- 焦点工件
- 前置工件
- 依赖工件
- 相关决策
- 派生结论
- 相关提交

### 任务重建

回答：

- 这个任务试图解决什么问题
- 哪些假设开启了它
- 它产出了哪些证据
- 它触发了哪些决策
- 它是否以结论闭环

### 目标重建

回答：

- 哪些任务实现了这个目标
- 哪些假设占主导
- 哪些决策影响了这个目标
- 是否已有足够结论来验证它

### 分支重建

回答：

- 哪条知识线在该分支中占主导
- 哪些工件与 `main` 分化
- 哪些决策只存在于该分支
- 哪些提交引入了这些差异

### 时间重建

回答：

- 某条知识线在提交之间如何演化
- 哪些节点出现了
- 哪些节点的状态发生了变化
- 哪些新证据推动了假设或决策

## 规范重建模型

重建应返回一个正式工件，例如：

```json
{
  "focus": {},
  "semanticThread": [],
  "timeline": [],
  "branchContext": {},
  "openQuestions": [],
  "gaps": []
}
```

### `focus` 字段

重建的主要节点或主要工作线。

示例：

- `task:123`
- `goal:abc`
- `hypothesis:xyz`

### `semanticThread` 字段

按语义连接的有序工件序列。

示例：

```text
Goal -> Task -> Hypothesis -> Evidence -> Decision -> Conclusion
```

每一步应包含：

- `entityType`
- `entityId`
- `relationship`
- `state`
- `summary`

### `timeline` 字段

相关历史事件序列。

每个事件应包含：

- 提交 id
- 分支
- 时间戳
- 变更类型
- 受影响工件
- 变更摘要

### `branchContext` 字段

分支元数据：

- 当前分支
- 头提交
- 相关提交
- 差异（如果存在）

### `openQuestions` 字段

线程尚不能关闭的问题。

示例：

- 缺少充分证据的决策
- 没有结论的假设
- 没有最终决策的任务

### `gaps` 字段

检测到的结构性缺口。
