How the GitHub-native CTX demo is delivered.

CTX uses GitHub Codespaces for the runnable viewer and GitHub Pages for the static landing. Pages explains the demo and the local MCP setup. Codespaces runs it.

Back To Landing Open In Codespaces

Why the split exists

GitHub Pages is static hosting. It cannot run the CTX Viewer backend or inspect a .ctx repository by itself. The runnable part therefore lives in a Codespace.

Canonical demo repository

The default demo dataset is examples/ctx/agent-session-continuity, chosen because it shows continuity across sessions instead of a one-shot graph.

If a temporary public viewer session is available, publish that URL on the landing page. Otherwise the canonical entrypoint stays the Codespaces quickstart.

Codespaces flow

  1. scripts/ensure-dotnet-sdk.sh installs the SDK pinned in global.json when needed.
  2. dotnet restore Ctx.sln runs on create.
  3. scripts/start-codespaces-demo.sh starts the viewer on 0.0.0.0:5271.
  4. The script sets CTX_VIEWER_DEFAULT_REPOSITORY_PATH to the tracked demo repo.
  5. Codespaces forwards port 5271 publicly.

Demo Repositories

  • /workspaces/ctx-open/examples/ctx/agent-session-continuity
  • /workspaces/ctx-open/examples/ctx/catalog-cache-branch-merge
  • /workspaces/ctx-open/examples/ctx/critical-checkout-regression

Manual relaunch

bash scripts/start-codespaces-demo.sh

Logs are written to /tmp/ctx-viewer-codespaces.log.

Delivery model

  • GitHub Pages = static landing
  • GitHub Codespaces = live viewer
  • Local MCP = your machine plus your MCP-capable agent
  • Local ACP = read-only session adapter through ctx-agent-acp
  • tracked .ctx example = demo data

Local MCP setup

The static page can prepare copy-ready configuration for each agent, but the MCP server itself still runs locally through ctx-mcp. The release smoke test is ctx_plan.
